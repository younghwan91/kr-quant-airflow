# Sharadar 동기화 검증 — raw 아카이브가 항상 벤더 최신본과 같음을 매일 보장한다

**결정일**: 2026-08-16
**상태**: 승인됨, 구현 착수
**개정 대상**: `2026-08-15-sharadar-bulk-rebuild-design.md` 의 스케줄 표(주기 3분할)

## 요구사항

> 구독 중인 Sharadar 데이터셋 **전부**가 매일 벤더 최신본과 동기화되어 있어야 한다.
> 그리고 그게 사실인지 매 실행마다 확인되어야 한다.

데이터가 비싸다. 받아놓고 안 쓰는 것도, 낡은 걸 최신인 줄 아는 것도 손해다.

**이 레포의 책임은 여기까지다.** raw 아카이브와 벤더의 동기화를 보장한다. 무엇을
어떤 테이블로 구울지는 `opt_portfolio` 가 정한다 — 지금 8개가 구워지고 6개가
raw 로만 남는 것은 그쪽 `load_csv` 의 reader 가 8종인 결과이지, 이 레포의 결정이
아니다(`opt_portfolio/factor/data/sharadar.py:299-308`). reader 가 늘면 이 레포는
`TABLE_KINDS` 에 한 줄 추가한다.

## 지금 이 계약이 깨지는 지점 (실측)

| # | 결함 | 근거 |
|---|---|---|
| 1 | `holdings` · `holdings_investor` · `descriptions` 는 **한 번도 받아진 적이 없다** | `dags/daily_sharadar.py:69` 가 `--cadence daily` 만 부른다. weekly·monthly 를 부르는 DAG 이 없다(`grep -rn sharadar dags/` 로 확인) |
| 2 | 벤더 목록에서 테이블이 사라지면 조용히 넘어간다 | `sharadar_bulk.py:85` 의 `if table in listing`. 경고는 plan 이 **통째로** 비었을 때만 난다(171행) |
| 3 | "오늘 벤더 최신본과 같은가"를 판정하는 코드가 없다 | `modified` 를 로컬 직전 값과만 비교한다. 벤더가 멈춰 타임스탬프가 그대로면 스킵하고, 로그에는 "변경 없어 건너뜀"으로만 남는다 |
| 4 | 무결성 확인이 파일 크기뿐이다 | `needs_download` 가 `size` 만 본다(132행). 체크섬은 이전 설계 51행에 있었으나 구현되지 않았다. zip 유효성 검사도 없어 손상은 빌드 단계까지 가야 드러난다 |

## 낡음과 손상을 구분한다

이게 이 설계의 중심 판단이다.

- **낡음** — 벤더가 아직 오늘 파일을 안 올렸다. 데이터 자체는 멀쩡하고, 벌크는
  매번 전체 이력을 주므로 **내일 받으면 빠진 하루가 저절로 채워진다.**
  → **막지 않는다.** 올라온 대로 굽고 공개하되, 무엇이 낡았는지 기록·보고한다.
- **손상** — 파일이 잘렸거나, 행수가 급감했거나, 이미 공개한 것보다 데이터가
  뒤로 갔다. **시간이 해결하지 않는다.** 그대로 공개하면 연구가 사라진 데이터
  위에서 돈다.
  → **막는다.** 기존 게이트(행수 5% 급감·최신일 후퇴)를 유지하고 체크섬을 더한다.

낡음을 막지 않기로 한 이유는 손익이 명백해서다. 벤더는 테이블마다 올리는 시각이
다르다(실측 KST: `holdings_ticker` 01:39, `insiders` 09:48, `daily` 12:56,
`stocks` 16:40, `fundamentals` 16:49, `funds` 16:54). DAG 은 17:30 에 돈다. 벤더가
한 시간만 밀려도 그날 그 테이블은 어제 것인데, 그것 때문에 나머지 13개의 갱신까지
포기하면 매번 손해다.

## 설계

### ① 주기 구분을 없앤다

`DAILY_TABLES` / `WEEKLY_TABLES` / `MONTHLY_TABLES` 와 `_CADENCES`, 그리고
`--cadence` 인자를 제거하고 **`SUBSCRIBED_TABLES` 단일 튜플 14개**로 바꾼다.
DAG 은 인자 없이 한 번 부른다.

주기 분할은 "542MB 를 매일 확인할 이유가 없다"는 판단이었는데, 요구사항이
"항상 동기화"라면 그 자체가 위반이다. 그리고 없앨 수 있다 — `modified` 비교가
있으므로 매일 14개를 확인해도 **안 바뀐 파일은 전송이 0바이트**다. 추가 비용은
목록 조회 1회뿐이고, 13F 542MB 는 실제로 바뀌는 분기당 한 번만 내려온다.

부수 효과로 결함 1이 사라진다. 안 돌던 DAG 을 두 개 더 만드는 대신 개념을
지우는 쪽이 맞다 — `wait_and_stop.sh` 가 메타DB 로 DAG 을 세므로 DAG 이 늘면
가동 창도 늘어난다.

### ② 목록 대조를 명시적으로 만든다

`plan_downloads` 를 `plan_sync(listing) -> (plan, missing)` 으로 바꾼다. 구독
목록에 있는데 벤더 응답에 없는 테이블을 `missing` 으로 반환하고, 호출부가 이를
보고한다. 지금처럼 조용히 빠지지 않는다.

`missing` 은 그 자체로 빌드를 막지 않는다(낡음 취급). 다만 그 테이블이 빌드
대상 8개 중 하나이고 로컬 파일도 없으면 `build()` 가 이미 `FileNotFoundError`
로 죽는다 — 그 경로는 그대로 둔다.

### ③ 정체를 센다

매니페스트 항목에 세 필드를 추가한다.

```json
"stocks.csv.zip": {
  "modified": "2026-08-16T03:56:19Z",   // 벤더 타임스탬프 (기존)
  "size": 953210472,                     // (기존)
  "sha256": "…",                         // 신규 — 손상 탐지
  "checked_at": "2026-08-16T17:30:12Z",  // 신규 — 마지막으로 벤더와 대조한 시각
  "unchanged_streak": 0                  // 신규 — modified 가 연속으로 안 바뀐 횟수
}
```

`modified` 가 바뀌면 `unchanged_streak` 는 0, 그대로면 +1 이다. `checked_at` 은
전송이 없어도 매 실행 갱신된다 — **"오늘 확인했다"의 증거가 이 필드다.**

미국 거래일 캘린더는 도입하지 않는다. 연휴에는 정체가 자연히 길어지고, 캘린더
없이도 "평소보다 오래 안 바뀌었다"는 신호는 잡힌다. 대신 "벤더가 상시 하루씩
늦다"는 만성 지연은 이 방식으로 못 잡는다 — 알려진 한계로 둔다.

정체 임계값은 테이블 성격에 맞춰 상수로 둔다. 넘으면 보고 표에 ⚠️ 로 표시할
뿐, 빌드를 막지 않는다.

| 테이블 | 임계 | 근거 |
|---|---|---|
| stocks · daily · fundamentals · tickers · actions · sp500 · funds · events · metrics | 2회 | 벤더가 매일 갱신한다 |
| insiders · holdings_ticker | 4회 | Form 4 · 13F 집계는 공시가 없는 날이 있다 |
| holdings · holdings_investor | 8회 | 13F 원자료는 분기 공시다 |
| descriptions | 30회 | 필드 사전. 2026-07-31 이후 무변경 |

### ④ 손상을 잡는다

- **체크섬** — 다운로드 직후 sha256 을 계산해 매니페스트에 남긴다. 다음 실행에서
  `modified` 가 같아도 로컬 파일의 sha256 이 다르면 손상으로 보고 다시 받는다.
  비용은 4.6GB 전량 재계산 기준 10초 안쪽이라 무시할 만하다.
- **zip 유효성** — 다운로드 직후 `zipfile.ZipFile(path).namelist()` 로 중앙
  디렉터리를 읽는다. 절단된 zip 은 여기서 예외가 난다. `testzip()` 은 전량
  압축 해제라 쓰지 않는다.

**기존 매니페스트를 무효화하지 않는다.** 키는 지금처럼 파일명을 쓰고, `sha256`
이 없는 기존 항목은 "미검증"으로 두되 재다운로드를 유발하지 않는다. 다음번에
그 파일을 실제로 받을 때 채운다. 키 체계를 바꾸면 첫 실행에 4.6GB 를 전량 다시
받게 되는데, 그럴 이유가 없다.

### ⑤ 동기화 상태를 보고한다

매 실행 끝에 14개 전부를 한 표로 찍는다. 이게 "동기화돼 있다"를 눈으로 확인하는
지점이고, 요구사항의 "확인되어야 한다"에 대응하는 산출물이다.

```
=== Sharadar 동기화 상태 (2026-08-16 17:34 KST) ===
테이블                 벤더 modified           크기      정체  판정
stocks                 2026-08-16T03:56:19Z   953.2MB     0   ⬇ 새로 받음
fundamentals           2026-08-16T03:51:02Z   626.4MB     0   ⬇ 새로 받음
descriptions           2026-07-31T02:10:44Z     0.9MB    12   ✓ 최신 (정적)
holdings               2026-07-15T04:02:11Z   542.1MB     9   ⚠️ 9회 연속 정체
metrics                —                          —       —   ⚠️ 벤더 목록에 없음
…
14개 중 최신 12 · 주의 1 · 누락 1   (전송 1,579.6MB / 4분 12초)
```

## 안 하는 것

- **낡음을 이유로 빌드를 막지 않는다.** 위 근거대로다.
- **미국 거래일 캘린더를 두지 않는다.** 정체 횟수로 대신한다.
- **스토어에 새 테이블을 만들지 않는다.** 6개(funds·events·metrics·holdings·
  holdings_investor·descriptions)는 raw 로만 최신 유지한다. 굽는 것은
  `opt_portfolio` 의 결정이고, 그쪽 reader 가 생기면 `TABLE_KINDS` 에 추가한다.
- **정규화를 이 레포로 가져오지 않는다.** 백만 달러 환산·`is_delisted` 리네임
  같은 규칙이 두 곳으로 갈라지면 과거 사고가 되살아난다.

## 테스트

`tests/test_sharadar_bulk.py` 를 확장한다. 기존 파일이 `opener` 를 주입받는
구조라 네트워크 없이 검증된다.

- 구독 목록 14개가 한 경로로 계획된다 — 주기 분기가 사라졌음을 고정
- 벤더 목록에 없는 테이블이 `missing` 으로 나온다 (조용히 빠지지 않는다)
- `modified` 가 같으면 `unchanged_streak` 가 증가하고, 바뀌면 0으로 돌아간다
- `checked_at` 이 전송 없이도 갱신된다
- sha256 이 어긋나면 `modified` 가 같아도 다시 받는다
- 절단된 zip 은 다운로드 단계에서 거부된다
- `sha256` 없는 기존 매니페스트가 재다운로드를 유발하지 않는다 (마이그레이션)
- 보고 표가 최신·주의·누락을 정확히 센다
